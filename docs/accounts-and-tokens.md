# User accounts and personal API tokens

This contract covers the authoritative Python controller and dashboard. The
implementation uses SQLite-backed identities and credentials. Experimental TypeScript and Rust paths do not
implement this account contract. Application, lease, enrollment, runner and
guest credentials retain their existing independent boundaries.

## Identity and ownership

Users have immutable UUIDs, case-insensitive usernames, an `admin` or `user`
role, and `pending`, `active` or `disabled` status. Public user records contain
`id`, `username`, `role`, `status` and `createdAt`. Password hashes, session
hashes and claim/token hashes are never public records.

An ordinary user can list, create and manage only their own machines. Ownership
also governs lifecycle requests, operation receipts, files, accessibility,
terminals and desktop connections. Administrators manage all machines. A new
machine receives its owner inside the creation transaction; callers cannot
choose or change that owner. Reusing another owner's machine or operation UUID
returns 404 before comparing a request body or returning an existing receipt.
Machine UUIDs remain globally unique for compatibility with existing runners.

Unowned machines are administrator-only. Existing non-lease machines are assigned
to the migrated administrator. If no administrator exists, first-admin setup
backfills those machines atomically. Lease assignments retain application/lease
ownership and are never adopted by ordinary users. Infrastructure, image
administration, inference jobs and consumer administration remain admin-only.
Users can read the offered template catalogue to create machines.

Authenticated responses include the current user ID, role and status. Disabling
an account invalidates its credentials. Authorization uses the current role,
never a role copied permanently into a session or token. No public registration,
user sharing, organizations, email delivery or external identity service is added.

## Sessions, invitations and recovery

Browser sessions use the existing HttpOnly, SameSite=Strict cookie and require
same-origin writes. Remote access requires HTTPS. API bearer credentials use the
Authorization header. The gateway rejects requests containing both bearer and
session-cookie credentials, and never accepts bearer credentials in query strings.
The direct controller continues rejecting browser Origin headers.

Admins create pending users and issue single-use, expiring invitations. Recipients
choose their own Canaveral password; admins do not set or receive it. An invitation
is delivered manually as a dashboard URL with `#claim=<secret>`. The page removes
the fragment immediately and submits the secret in a POST body. It is never a
query parameter or API token. Invitation and reset claims last 24 hours; first-admin
bootstrap claims last 15 minutes. Only hashes are persisted. Claim redemption and
consumption occur atomically. A lost claim response requires sign-in or an explicit
new invitation, not automatic password-setting replay.

Claim `kind` values are `bootstrap`, `invite` and `reset`. API timestamps are Unix
seconds. Token creation returns flat token metadata with an additional `token`
secret on its first response; a replay omits that secret.

Passwords retain the existing salted PBKDF2-HMAC-SHA-256 representation and
12–1024-character limits. Expensive derivation occurs outside SQLite write locks,
with credential/status revalidation before committing a new session. Sign-in and
public claim attempts have persistent, bounded rate limits and generic failures.
Sign-in and claim requests share a ten-attempt-per-minute controller budget across
replicas. Exhausting it temporarily delays other users and recovery claims too;
the budget resets after 60 seconds. Per-client throttling is not implemented.

Password change and admin-assisted reset revoke that user's sessions and personal
API tokens. Issuing a reset also blocks the previous password immediately until
the reset claim is redeemed. Reset preserves the user ID and machine ownership.
Re-enabling a disabled account explicitly returns it to pending, clears its old
password and requires a fresh invitation before it can sign in. Account/role changes
must not remove the last active administrator. A separately authenticated operator
can perform explicit recovery without deleting the identity or its machines.
The existing operator-backed localhost first-admin flow remains supported. An
operator can also issue a short-lived bootstrap link for remote first-admin setup.

## Personal API tokens

Tokens belong to a user and have a caller-supplied UUID `id`, `name`, `scopes`,
`createdAt`, `expiresAt`, `lastUsedAt`, `revokedAt` and a safe identifying `prefix`.
The secret is generated by the controller and returned once on creation; storage
contains only its hash. Lists and replays return metadata without the secret.
Never log credential responses. A lost creation response is recovered by inspecting
the named token, explicitly revoking it and creating a replacement with a new UUID.

| Scope | Access |
| --- | --- |
| `machines:read` | Own machine inventory, status and permitted templates |
| `machines:write` | Create and change lifecycle of own machines |
| `machines:access` | Own guest operations and their results, files, accessibility, terminal and desktop connections |
| `admin` | Human administration, only while the token owner is an active admin |

Sessions receive their role's full access. Token authority is the intersection of
its scopes, current account/role and machine ownership; scopes cannot confer
another user's machine access. `admin` includes the machine scopes. Human tokens
never enroll runners or replace application/lease credentials. Only login sessions
can create personal tokens; a token cannot mint another personal token.

Expiry defaults to 30 days and is mandatory, with a maximum of 365 days. Clients
send an integer `expiresInSeconds` between 60 and 31,536,000 when overriding it.
Revocation is idempotent and remains visible in token metadata. Last-use timestamps
are updated at most once per minute. Restricting scopes and changing account status
take effect on subsequent authorization checks. Established connections recheck
authorization periodically and before forwarding bytes after blocking reads.

Administrators can list personal token metadata for every user and revoke a
selected token. This list includes expired and revoked tokens, ordered by
creation time and token UUID, with the owner's `userId` alongside the same safe
metadata as the personal list. It is a single unpaginated snapshot, like the
user list. It never includes token secrets, credential hashes, passwords or
login-session records. It provides no way to create a token for another user.
Both an active administrator session and an active administrator's token with
the `admin` scope can use these routes; the operator credential also retains
administrative access.
The current role and credential status are checked in the same transaction as
the list or revocation. Repeated revocation preserves the original `revokedAt`.
Revoking the caller's own API token succeeds, then subsequent use is rejected;
revoking an API token does not revoke its owner's separate browser session.

## HTTP interface

JSON POST bodies reject unknown fields. User and token management routes require
the appropriate current principal; missing or foreign resources return 404.

| Method and path | Body / result |
| --- | --- |
| GET `/v1/auth/status` | Existing first-admin setup status |
| POST `/v1/auth/setup` | Existing operator-only `{username,password}` bootstrap |
| POST `/v1/auth/login` | `{username,password}`; session and user |
| GET `/v1/auth/session` | Current login-session identity; API tokens cannot impersonate cookie sessions |
| POST `/v1/auth/logout` | `{}`; revoke current login session |
| POST `/v1/auth/password` | `{currentPassword,password}`; revoke user sessions/tokens |
| POST `/v1/auth/bootstrap` | Operator only, `{}`; one-time bootstrap claim metadata and `token` |
| POST `/v1/auth/claim/info` | `{token}`; claim `kind`, `username` when known, `expiresAt` |
| POST `/v1/auth/claim` | `{token,password,username?}`; choose username only for first-admin claim; new session |
| GET `/v1/users` | Admin only; `{users:[...]}` |
| POST `/v1/users` | Admin only; `{id,username,role?}`; pending user (role defaults to `user`) |
| POST `/v1/users/{id}/update` | Admin only; `{role?,status?}`; disable with `disabled`; re-enable to `pending` and issue a fresh invitation; `active` cannot bypass password setup |
| POST `/v1/users/{id}/invite` | Admin only, pending user, `{}`; replacement one-time claim and `token` |
| POST `/v1/users/{id}/revoke-invite` | Admin only, `{}`; revoke unused claims |
| POST `/v1/users/{id}/reset-password` | Admin/operator only, `{}`; revoke credentials and issue reset claim |
| GET `/v1/auth/tokens` | Login session only; `{tokens:[...]}` for current user |
| POST `/v1/auth/tokens` | Login session only; `{id,name,scopes,expiresInSeconds?}`; metadata and one-time `token` |
| POST `/v1/auth/tokens/{id}/revoke` | Login session only, `{}`; idempotent own-token revocation |
| GET `/v1/admin/tokens` | Admin only; `{tokens:[...]}` for all users, safe token metadata plus `userId` |
| POST `/v1/admin/tokens/{id}/revoke` | Admin only, `{}`; idempotent revocation, safe token metadata plus `userId` |
| GET `/v1/machines/{id}` | Visible machine; requires `machines:read` |
| POST `/v1/machines/{id}/authorize` | `{action}` where action is `read`, `write` or `access`; exact machine authorization |

The dashboard proxies these routes under `/api`. Its direct connectors use exact
machine/action authorization before attaching and throughout streaming. A successful
inventory or session request is insufficient authorization to touch a guest.

## CLI workflow

These commands use the controller origin in `--url` (the dashboard origin is
separate). The controller must already be running. Replace origins and paths for
your installation. Credential and link output files must not exist beforehand;
their parent directories must already exist and have appropriate permissions.
Files are created with POSIX mode 0600; Windows directory ACLs still apply.

For remote first-admin setup, an operator creates a private link file:

```sh
python3 -m canaveral --url https://controller.example.internal \
  --token-file ./secrets/admin.token admin setup-link \
  --dashboard-url https://canaveral.example.internal \
  --output-file ./secrets/first-admin.link
```

Open the link in that file within 15 minutes and choose a Canaveral username and
password. The operator credential stays on the operator's machine. The command
prints safe metadata and the file path, never the link secret.

After activation or invitation acceptance, save a login session privately:

```sh
python3 -m canaveral --url https://controller.example.internal login \
  --username alice --output-file ./secrets/alice.session
```

The password prompt is hidden. `--password-file` accepts an already protected file
for noninteractive use. A personal session can list visible machines and mint a
read-only automation token:

```sh
python3 -m canaveral --url https://controller.example.internal \
  --token-file ./secrets/alice.session machines
python3 -m canaveral --url https://controller.example.internal \
  --token-file ./secrets/alice.session tokens create --name inventory \
  --scope machines:read --expires-in 2592000 \
  --request-id 80325a82-78ce-45ee-aeb3-cc624e5248eb \
  --output-file ./secrets/inventory.token
python3 -m canaveral --url https://controller.example.internal \
  --token-file ./secrets/inventory.token machines
```

Use a fresh UUID for each token. Preserve its UUID through an uncertain response;
never silently mint a replacement. `tokens list` with the login-session file
shows the original record without its secret. `tokens revoke <token-id>` revokes
it. Add `machines:write` and `machines:access` explicitly for automation that
creates machines and controls guests. Personal tokens cannot mint more tokens.

An admin session or operator credential can run `users list`, `users create
--username alice --request-id <uuid>`, `users invite <user-id> --dashboard-url
<origin> --output-file <new-file>`, and `users update <user-id> --role user
--status disabled`. `users reset-password` issues a recovery link while preserving
machine ownership; `users revoke-invite` cancels unused links. An operator can
recover the last administrator with `admin recover --user-id <user-id>
--dashboard-url <origin> --output-file <new-file>`.

`account password` prompts for the current and new password, revokes existing
sessions/tokens and removes the local revoked session file. `logout` revokes the
current login session before removing its credential file. Neither command
removes an operator/API-token file masquerading as a login session.

## Upgrade and verification

Migration is transactional and idempotent, including concurrent startup. It copies
the legacy administrator's existing hash and still-valid sessions into user-bound
records, marks the legacy credential tables consumed, and prevents a restart from
resurrecting revoked sessions. Credential rows in legacy tables must not remain a
second accepted login authority. Back up the controller database before live
upgrades; running an older authentication implementation against an upgraded
database is unsupported and must fail closed where detectable.

Required fixtures cover two ordinary users and an admin, all machine/receipt and
direct-connector authorization paths, revocation during streams, credential-type
separation, scope/expiry rules, claim replay/races, last-admin protection, and
legacy migration/restart behavior. Fixture coverage does not establish native
provider or cross-network acceptance.
