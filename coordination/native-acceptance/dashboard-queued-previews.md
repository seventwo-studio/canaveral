# Native queued dashboard preview acceptance

Run `dashboardQueuedPreviews` from `dashboard-queued-previews.mjs` with the PR61 disposable native dashboard adapter, the [PR60 verified ARM64 bundle and signed helper](pr60-native-preview.md), one dashboard account and the dashboard TLS ingress used by the [preview trials](README.md#dashboard-workspace-preview-trials). Use a one-box resource domain. Give the dashboard its own granted application, separate from the application that fills the domain, so the preview waits for physical capacity rather than its own box limit.

The adapter supplies the callbacks documented in the module. `fill` boots a workspace for the other application. `onWaiting` and `onCancelled` check that the preview's request holds no lease and that the domain still has exactly one reservation. `restart` closes the dashboard, waits for its close event and creates a new server on the same preview database. `free` releases the filler and waits for its positive cleanup; the harness report check must expect the waiting preview's admission as the successor. `onLaunch` waits for admission and starts the satellite for the preview's lease without changing the dashboard's lease credential. `onCleanup` verifies controller cleanup, satellite exit, helper and owned VM process exit, removal of the machine directory, workspace and relay, and zero reservations. Never stop, inspect or count unrelated VM processes. Keep credentials, raw databases and private harness output out of the repository.

## 2026-11-19 observations

The trial ran on the ARM64 Mac Studio homelab node with a disposable loopback TLS controller, a fresh runner enrollment, the Rust satellite and runner client built from this change, and the dashboard built from this change. The adapter verified the helper signature and the bundle pins. The domain held one 2-CPU, 4096-MiB, 8-GiB workspace. One Virtualization process that existed before the trial was left untouched and was still running afterwards; the trial's processes were attributed by their own machine directories.

A workspace for the filler application booted to ready. The dashboard then accepted two static previews and replayed each submission. Both reported `provisioning` with request state `waiting`, and `expiresAt` equal to their waiting deadlines. Neither had a lease, and the domain kept exactly one reservation. Owner cancellation of the second preview ended it `stopped` with request state `cancelled` and reason `consumer_cancelled`; it never received a lease. After the dashboard server was closed and recreated on the same database, the first preview was still `provisioning` and waiting.

Releasing the filler produced a complete cleanup report. The satellite exited, the helper and its owned VM process were gone, and the machine directory, workspace and relay were removed. The controller admitted the waiting preview in the same step; the domain count stayed at one reservation. Its lease expiry was the admission time plus the 240-second preview TTL. A second satellite booted that workspace. The dashboard uploaded the files, started the supervised static service and reported `ready` with request state `admitted`. Through a single-use handoff on the private preview origin, the page and its nested script returned 200 with the exact uploaded bytes.

Owner release ended the preview `stopped`. Cleanup was complete, the satellite exited, the helper and owned VM process were gone, the machine directory, workspace and relay were removed, and the stopped, cleaned and released journal flags were set. The previously opened origin returned 404 and the domain returned to zero reservations. This trial did not exercise priority ordering, fairness between applications, deadline expiry, lost replies or revocation natively; portable tests cover those.
